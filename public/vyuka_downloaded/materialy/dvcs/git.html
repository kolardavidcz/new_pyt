Git

by Jiří Znamenáček

1

Identifikace

První věc, kterou musíte udělat, aby byl git vůbec ochotný se s vámi bavit, je identifikovat se. Provádět změny v repozitáři totiž můžete pouze tehdy, když je možné je s někým svázat.

Tuto identifikaci můžete provést z příkazové řádky: 

    $ git config --global user.name "Pirat Piratovic"
    $ git config --global user.email Pirat.Piratovic@example.com

Druhou možností je objevit, kde se na vašem systému schovává soubor konfigurací gitu .gitconfig a upravit v něm příslušnou část [user]: 

    [user]
        name = Pirat Piratovic
        email = Pirat.Piratovic@example.com
📝
Na Linuxu bude cesta /home/UserName/.gitconfig, na (novějších) Windows c:\Users\UserName\.gitconfig.
2

„.gitconfig“

Soubor .gitconfig toho ale může obsahovat mnohem více. Ukažme si příklad: 

    [user]
        name = Pirat Piratovic
        email = Pirat.Piratovic@example.com
    [core]
        editor = Notepad2.exe
        excludesfile = .gitignore
    [color]
        ui = true
    [alias]
        unstage = reset HEAD --
        last = log -1 HEAD
        visual = gitk

Význam uvedených bloků je následující:

  • [user] : vaše identifikace (jako uživatele gitu)
  • [core] : několik významných nastavení pro git (např. vyžádá-li si git použití editoru, bude díky tomuto nastavení použit program Notepad2.exe)
  • [color] : velmi užitečné nastavení, které šikovně obarví výstupy jednotlivých příkazů
  • [alias] : velmi užitečná část sloužící k zavedení zkratek za složitější příkazy gitu (s tímto nastavením snadno odsunu soubor z indexu pomocí příkazu git unstage SOUBOR)
3

Adresář „.git“

Veškerá „magie“ gitu se schovává ve speciálním podadresáři .git kořenového adresáře vašeho projektu.

Tento adresář – kromě dodatečných nastavení a řídicích souborů – totiž především obsahuje (v podobě binární databáze) veškerý obsah daného projektu, a to včetně jeho kompletní historie.

📝
Má-li váš projekt dlouhou historii nebo obsahuje-li mnoho velmi rozdílných vývojových větví, nedivte se, že tento adresář bude velmi veliký – musí v sobě všechny tyto údaje zaznamenat. Pravděpodobně poměrně brzo překročí jeho velikost velikost samotného projektu.

PS: Git narozdíl od většiny ostatních verzovacích systémů neukládá rozdíly ve změněných souborech (tzv. delta-based přístup), ale celkový stav celého projektu v podobě tzv. snapshotů (snad „snímků“?). Komit u Gitu tak znamená vytvoření SHA-součtů všech souborů a adresářů a uložení záznamu (opět označeného pomocí SHA-heše) o všech těchto součtech a jejich provázání s příslušnými binárními podobami souborů v lokální „databázi“. Vlastní komit je pak zase jenom SHA-označený ukazatel na tento přehledový záznam. (A těchto ukazatelů můžete mít, co hrdlo ráčí. Proto se v Gitu tak dobře pracuje s vedlejšími vývojovými větvemi.)

4

Globální versus lokální nastavení

Nastavení z předchozích slajdů jsou globální, platí pro vaši veškerou komunikaci s libovolnými repozitáři a nachází se v globálním konfiguračním souboru .gitconfig.

Kromě toho si však každý repozitář drží ve svém .git-adresáři také tzv. lokální konfiguraci, v souboru config. Její struktura je úplně stejná, takže ji buď můžete přepisovat přímo nebo pomocí nastavení z příkazové řádky, jen s vynecháním přepínače --global, tj. například: 

    $ git config user.name "Pirat Piratovic"
    $ git config user.email Pirat.Piratovic@example.com

Zde uvedená nastavení jsou platná pouze pro uvedený repozitář. Hodí se tedy například, potřebujete-li pro daný projekt používat jinou identifikaci nebo třeba jiný seznam ignorovaných souborů.

5

Ignorované soubory

Narozdíl od Mercurialu umožňuje git jméno a cestu k souboru pro uložení vzorů ignorovaných souborů konfigurovat. Na jednu stranu bezva, na druhou bez pohledu do konfigurace nevíte, která bije.

📝
Dále se proto budeme držet úmluvy, že uvedený soubor se nachází na stejném místě jako hlavní konfigurační soubor .git a bude se jmenovat .gitignore.

Příklad: Následující jednoduchý .gitignore-soubor.. 

    *~
    *.pyc

..způsobí, že git nebude záložní soubory (unixových) textových editorů (vzor *~) a zkompilované pythoní moduly (vzor *.pyc) vůbec uvažovat za hodny své pozornosti ^_~

6

„clone“ & „init“

Vytvořit repozitář můžete dvojím způsobem:

  • naklonováním již existujícího repozitáře příkazem git clone: 
                git clone <ADRESA>
    📝
    Výsledkem bude nový podadresář klonovaného projektu v aktuálním adresáři.
  • založením nového repozitáře příkazem git init: 
                git init <ADRESÁŘ>
    📝
    Také můžete adresář vytvořit dopředu, přepnout se do něj a zavolat pouze git init, výsledek bude stejný.
7

„add“, „commit“ a tzv. index

Soubory, jejichž aktuální stav chcete do repozitáře přidat, musíte nejprve označit příkazem git add a následně pomocí příkazu git commit do repozitáře zanést: 

    git add <SOUBOR-1 SOUBOR-2 …>
    git commit                       # vyvolá externí editor pro zadání zprávy
    git commit -m "ZPRÁVA PRO LOG"   # zpráva přímo na příkazové řádce

Týká se to jak souborů zcela nových (jimž tedy chcete začít udržovat jejich historii), tak ale i souborů již verzovaných, ale nedávno změněných (čímž se git liší prakticky od všech jiných DVCS). Z technického hlediska se u gitu mezi přidáním a komitem do repozitáře nachází ještě tzv. index (staging area), což prakticky vlastně znamená, že výchozí chování příkazů add i commit je:

„Nedělej nic, co si uživatel výslovně nevyžádal.“

Příkaz commit tak do repozitáře (historie) zanese pouze ty změny, které byly uživatelem nejdříve zaneseny do indexu pomocí příkazu add, který je tak narozdíl od jiných DVCS používaný mnohem častěji (pro každou změnu každého souboru). Pro pohodlí uživatele však existují některé užitečné zkratky:

  • git add . – přidá do indexu všechny změněné soubory (či adresáře) v aktuálním adresáři a jeho podadresářích;
    📝
    Můžete napsat třeba i ../. pro přidání všeho od nadřazeného adresáře. Tudíž pouze v kořenovém adresáři repozitáře budou přidány opravdu všechny změny.
    📝
    PS: Do verze 2 se mezi změny nepočítaly smazané soubory, ale tak starou už snad nikde nepotkáte.
  • git commit -a – nejdříve přidá do indexu všechny provedené změny a poté je rovnou nakomituje.
    📝
    Ale to se týká pouze v repozitáři již zanesených souborů, úplně nové musíte přidat ručně.

Poznámka: Verze git commit s externím editorem (tedy bez přepínače -m) má jednu výhodu – rozhodnete-li se při psaní komit-zprávy, že vlastně ještě nic komitovat nechcete, stačí editor prostě bez ukládání zapsané zprávy zavřít a ke komitu nedojde.

8

„status“

Rozdíl mezi novými či upravenými soubory/adresáři v kódu a soubory či adresáři, které budou zaneseny do historie, je nejlépe vidět pomocí příkazu status.. 

    git status [-s|--short]

..který obě skupiny změn – provedené změny versus změny zanesené do indexu (a tudíž připravené pro příští komit) – od sebe striktně rozlišuje.

📝
A to tím spíš, pokud jste si ve svém .gitconfig povolili obarvování výstupu (které je podobně jako u samotné linuxové příkazové řádky podle mě zcela nesmyslně z historicko-ideologických důvodů ve výchozím nastavení vypnuté) – provedené změny jsou označeny červeně, změny navíc zanesené do indexu jsou označeny zeleně.

Je však třeba si zapamatovat následující:

Změníte-li soubor již zanesený do indexu, nakomitována bude jeho verze z indexu, nikoli jakákoli změna provedená po jeho přidání do indexu.

Chcete-li nakomitovat verzi novější, musíte nejdříve přidat verzi novou (git add SOUBOR) a teprve poté ji nakomitovat (git commit).

📝
PS: A dřív jste dokonce museli nejdřív starší verzi z indexu odstranit (viz alias git unstage SOUBOR).

PS: Git tedy zcela netradičně umožňuje v rámci jednoho komitu zanést (a stejnou komitovací zprávou označit) pouze část změněných souborů. To může být velmi mocný nástroj, ale ruku v ruce s tím i velmi nebezpečný (stačí si představit třebas neúmyslný komit pouze části upravených souborů potřebných pro běh programu a jejich propagaci do cizího repozitáře).

9

„rm“

Zbavit se souborů již zaznamenaných v historii (tedy nakomitovaných) je na první pohled trochu obtížnější úkol. Smažete-li totiž soubor/adresář „jen tak“ v souborovém systému, budete muset git přesvědčit (pomocí git add), že to myslíte vážně a že to nebyla jen nějaká náhoda (což je ostatně ten hlavní důvod, proč to funguje právě takhle). Chcete-li tedy nějaký soubor(y) při příštím komitu smazat, použijte rovnou příkaz git rm, který soubor odstraní na souborovém systému a rovnopu změnu zanese i do indexu: 

    git rm SOUBOR1 [SOUBOR2 …]
📝
Navzdory své úmyslné „ukecanosti“ následuje v tomto případě git linuxovou příkazovou řádku, takže příkaz git remove není k dispozici.

Při odstraňování souborů pomocí git rm (tedy zároveň ze souborového systému i se zanesením do indexu) však git kontroluje, zda jste mezitím uvedený soubor nějak nezměnili (případně už danou změnu i nezanesli do indexu), a změněný soubor odmítne odstranit. Přepínač -f, resp. --force, pomůže: 

    git rm -f soubor

K dispozici je (mimo jiné) ještě další užitečný přepínač: 

    git rm -n
    git rm --dry-run

Ten prozměnu žádné odstranění neporovede, ale ukáže vám, co by bylo odstraněno, pokud byste tento přepínač vynechali. Velmi užitečné pro hromadné odstraňování více souborů či adresářů.

10

„mv“

A to samé se pochopitelně týká i přejmenovávání. Potřebujete-li nějaký soubor nebo adresář přesunout či přejmenovat, můžete rovnou použít příkaz.. 

    git mv Cesta1 Cesta2

..který uvedenou změnu rovnou promítne i do indexu (takže na vás zbývá už jen potvrzující komit).

Na druhou stranu – git je často natolik schopný, že provedete-li uvedené změny na souborovém systému, pozná přesunutí/přejmenování v naprosté většině případů sám a před komitem vám je správně přiřadí a nahlásí.

11

Náprava běžných chyb

Někdy se neubráníte a uděláte nechtěně nějakou chybu, typicky nenakomitujete všechny soubory, které jste měli (obzvlástě snadné opomenutí v gitu s jeho indexem). Pro tyto případy existuje mnoho různých náprav, od relativně bezpečných až po zcela katastrofální. Ukažme si pár z nich:

Naprosto typickou chybou při používání gitu (kde máme k dispozici index) je přidání více souborů k příštímu komitu, než jsme chtěli. Náprava je jednoduchá a git nám ji dokonce hlásí ve výchozí nápovědě příkazu status: 

    git reset HEAD SOUBOR
📝
Celkem doporučuji zavést si na tohle alias unstage.

Poměrně bezpečná je také náprava úvodního příkladu – komitovali jste příliš brzo a zbrkle. Dokud na nic jiného nesáhnete, můžete doplnit index o zapomenuté soubory (pomocí git add) a následně zavolat: 

    git commit --amend

Výsledkem této operace je na první pohled jediný komit – ten poslední, opravený.

📝
Pokud o to budete hodně stát, dá se k „zapomenutému“ komitu ale také dostat.

Naprosto úžasné použití pro tento příkaz je obzvláště ve chvíli, kdy se upíšete při psaní komitovací zprávy – prostě komitnete znovu, tentokrát (snad :-) už se zprávou správnou.

Na druhou stranu někdy si pracovní adresář tak rozvrtáte, že byste nejradši všechno zahodili a začali znova od posledního komitu. To už je dost nebezpečná operace – přijdete o všechny změny, které jste od posledního komitu udělali! Proto si aplikaci následujících příkazů (zvláště toho druhého!) nejdříve dobře rozmyslete: 

    # pro jeden konkrétní soubor (a nesmí být v indexu)
    git checkout -- SOUBOR

    # pro všechny změny v celém repozitáři
    git reset --hard
📝
Správnější postup, jak tohle zařídit, je dělat nové změny v testovací větvi a do hlavní je promítat pouze při jejich úspěšném zvládnutí. Na to ostatně byl Git mimo jiné vymyšlen.
12

Náprava (méně) běžných chyb

Někdy ovšem uděláte komit, který je z podstatné části správně, ale z hodně velké také ne. Nejradši byste se vrátili zpátky před něj a nakomitovali tentokrát pouze to, co si to skutečně zaslouží. Světe (ne)div se, jde to:

📝
Velké díky za Stack Overflow.

Ve všech případech budeme začínat od následující struktury komitů: 

         (F)
    A—B—C—D
          ↑
        master

To jest: Ze stavu C jsme provedli (uspěchaný) komit do stavu D. Tento stav je tudíž aktuálním masterem a naše pracovní soubory (F) vypadají podle něj.

Pokud se chcete vrátit do stavu před komitem D, ale přitom nepřijít o změny z tohoto komitu, tedy chcete vlastně udělat toto.. 

         (F)
    A—B—C—D
        ↑
      master

..náprava je naštěstí jednoduchá: 

        git reset HEAD~1

Po provedení tohoto příkazu budou vaše soubory vypadat přesně tak, jak vypadaly, než jste je začali přidávat do indexu a komitovat.

Mimochodem existuje dokonce varianta předchozího příkazu, která se vrátí v čase o kousek blíže – „zahodí“ sice komit D s ponecháním souborů v rozpracovaném stavu, ale nesáhne na index, který komitu D příslušel: 

        git reset --soft HEAD~1

Z hlediska souborů je výsledek tedy stejný jako bez parametru --soft, ale staging area zůstala zachovaná ve stavu pro komit D.

Pokud chcete zahodit nejen nepovedený komit, ale i celou rozpracovanou práci, stačí napsat.. 

        git reset --hard HEAD~1

..jak jsem zmiňoval už na předchozím slajdu.

📝
Zajímavé na gitu je, že ani v tomto případě jste o komit D nepřišli (alespoň po nějakou dobu) – git si totiž pamatuje veškerou provedenou historii (alespoň do příští údržby repozitáře), i když ji neukazuje ve stromečku provedených komitů (protože z něj jsme ji vlastně tímto příkazem odstranili). Chcete-li se ke komitu D dostat, musíte ho nejdříve najít v kompletní historii příkazem git reflog a následně ho příkazem git checkout -b NováVětev SHAOdstraněnéhoKomitu „vytáhnout“ (zde tedy pochopitelně do jiné větve).
13

gitk

Narozdíl od mercurialu (hg serve) nemá git žádný vlastní jednoduše přístupný interní webový server s grafickým rozhraním. Na druhou stranu je ale zase téměř nemožné nainstalovat git bez dedikovaného GUI-nástroje gitk, jehož obdoba je v mercurialu dostupná jenom jako rozšíření, a ještě ke všemu nepodporované. Doporučuji pouštět ho z příkazové řádky uvnitř projektu na pozadí, tj.: 

    gitk &
14

„log“

Na historii repozitáře se samozřejmě můžete podívat i z příkazové řádky. K tomu slouží příkaz git log. Nejzákladnější použití spočívá ve výpisu logu pro celý repozitář.. 

    git log

..nebo pouze pro vybraný soubor: 

    git log SOUBOR/ADRESÁŘ

Poznámka: Příkaz git log má k dispozici neuvěřitelnou spoustu doplňujících přepínačů, kterými můžete jeho výstup velmi ovlivnit. Kupříkladu přepínačem -n ČÍSLO (resp. --max-count ČÍSLO) říkáte, jak daleko do historie se má při výpisu zajít (obzvláště užitečné pro dlouhé historie).

15

„diff“ & „whatchanged“

Druhým základním příkazem pro prozkoumávání stavu repozitáře z příkazové řádky je příkaz git diff. Jeho použití je podobně jako u git log mnohostranné, ale mezi základní patří:

Porovnání aktuálního stavu souboru vůči poslednímu stavu v historii je díky existenci indexu trojí: 

    git diff SOUBOR             # pracovní dosud nepřidané v indexu
    git diff --cached SOUBOR    # index versus repozitář
    git diff HEAD SOUBOR        # pracovní versus repozitář
📝
Prostě si musíte dávat pozor na to, že git komituje pouze věci přidané do indexu. I když jste třeba ty samé soubory mezitím ještě víc rozhrabali.

Často se hodí porovnat dvě historické verze jistého souboru nebo adresáře: 

    git diff StaráRevize..NováRevize SOUBOR
📝
Pro rozlišení revizí je třeba zadat jejich číselné označení v historii, které zjistíte třeba z příkazu git log SOUBOR. Vzhledem k charakteru těchto čísel často stačí vzít prvních pár znaků, nemusíte je kopírovat celá.
📝
Pro některé historické „milníky“ jsou k dispozici speciální pojmenování. Např. HEAD^..HEAD porovná poslední komit s jeho prvním rodičem. Více viz samostatná kapitola.

git diff se dá použít i bez udání konkrétního souboru, pak se použije na změny v celém projektu. Ale lepší je pak použít speciální příkaz git whatchanged: 

    git whatchanged StaráRevize..NováRevize
📝
Pro rozlišení revizí je třeba zadat jejich číselné označení v historii, které zjistíte třeba z příkazu git log.
16

Práce se vzdáleným repozitářem

Git by nebyl distribuovaným systémem, kdyby neumožňoval spolupráci s externími repozitáři (a také práci s vývojovými větvemi, ale to je námět příslušné části samostatné kapitoly).

Základním předpokladem je mít v konfiguraci nastavenu cestu k externímu repozitáři a způsob provázání externích a místních větví (položky [remote …] a [branch …] v .git/config). Pro repozitář naklonovaný z externího zdroje není co řešit, uvedené informace bude automaticky obsahovat.

📝
Přidáváte-li remote dodatečně, použijete nejspíš příkaz git remote s některými z jeho mnoha přepínačů.

Po splnění tohoto požadavku můžete používat především následující příkazy:

  • git pull – stáhne změny z externího repozitáře k vám (git fetch) a rovnou je promítne do pracovního adresáře (git merge FETCH_HEAD)
    📝
    Dejte si pozor na stav vašeho a externího repozitáře a také na jména větví, která se budou spojovat – je velmi snadné dostat se do problematického konfliktu ^_^
  • git push – vypropaguje vaše lokální změny (ty již nakomitované) do externího repozitáře
    📝
    Aby to fungovalo, váš lokální repozitář musí obsahovat všechny změny repozitáře externího. A vzdálený repozitář musí být typu bare.
17

PS: Řešení problémů se spojením přes SSH

Komunikace se vzdáleným repozitářem bude dosti pravděpodobně probíhat pomocí zabezpečeného protokolu SSH. A když selže, je někdy dosti pracné zjistit, co se vlastně porouchalo. Samotné ssh na to má přepínače -v až -vvv, v případě Gitu je to velmi podobné, jen kapku složitější na zadání: 

        GIT_SSH_COMMAND="ssh -v" git …

Opět podle potřeby můžete příznak -v (aneb verbose) namnožit až na trojnásobek, ale často už první úroveň odhalí problém.

18

„help“

Cítíte-li se ztraceni, nezoufejte – příkaz git help je tu vždy k vašim službám! Pár příkladů:

  • Vypiš nejdůležitější, respektive všechny příkazy gitu: 
                git help        # základní
            git help -a     # všechny; též „git help --all“
    📝
    Samotný příkaz git zafunguje úplně stejně jako git help, vypíše tedy základní nápovědu.
  • Vypiš plnou nápovědu pro konkrétní příkaz gitu: 
                git help PŘÍKAZ
    📝
    Způsob výpisu se dá volit mezi klasickými man-pages, ne tak klasickými info-pages a výstupem v HTML-podobě na web. Pod Windows je k dispozici pouze výstup na web.
